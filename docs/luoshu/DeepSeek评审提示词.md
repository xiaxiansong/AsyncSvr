# 洛书多机型适配测试用例 —— 内部 agent 一次性评审提示词

## 使用方法

前提：agent 的启动目录就是 swing 项目源码根目录，`docs/luoshu/` 和历史测试用例都已放在源码根目录下。

把下面代码块里的内容整段发给 agent 即可，不需要改任何路径。

---

```text
# 任务
你是华为终端鸿蒙系统能力 swing_service 的测试专家，也是本任务的主 agent（总协调者）。请评审并完善“洛书（AI伴随）多机型适配”的真机手工测试用例，最终输出一个 Excel 文件。文件中要包含所有机型的公共测试用例，以及三折叠、双折叠、阔折叠、小折叠各自的专项测试用例。

本任务要求你充分使用子 agent：凡是互相独立的工作都并行交给子 agent，你本人只负责拆分任务、派发、汇总、裁决冲突和最终生成文件，不要亲自逐条评审用例。

# 本次需求的两个目标（所有子 agent 都要围绕这两点工作）
1. 洛书（AI伴随）在各机型、各形态下都能正常使用。对应用例的“预期结果”列（功能表现）。
2. swing_service 中洛书相关部分正常运行，不出现报错和不符合预期的行为。对应用例的“swing_service 核对点”（日志）列，以及《行为基线》页。
两项都满足才算用例通过。其中目标 2 的判定标准必须来自源码，不能凭推断。

# 输入（当前工作目录就是 swing_service 源码根目录，以下路径都相对于它）
- 源码：当前目录。读源码时排除 docs/luoshu/、docs/luoshu/review_work/、历史测试用例文件和编译产物。
- 待评审用例：docs/luoshu/
  - 洛书多机型适配测试用例.md：用例的可读版本
  - cases.py：用例数据源（COMMON/TRI/DUAL/WIDE/FLIP 列表、DIMS 覆盖维度、SUPPORT 支持性、SCENARIOS 支持场景清单、BASELINE 行为基线（内容待填）、GENERIC_CHECK 通用检查、NON_MANUAL 非手工项）；文件开头的注释是 AI伴随交互说明
  - gen.py：在源码根目录运行 `python3 docs/luoshu/gen.py docs/luoshu`，由 cases.py 生成 Excel 和 md
- 历史测试用例：放在源码根目录下（不在 docs/luoshu/ 里）。开始前先在根目录找出这些文件（如 .xlsx/.xls/.csv/.md 格式、文件名含“用例/测试/testcase”等），把文件清单写入 docs/luoshu/review_work/history_cases_list.txt，并告诉每个需要参考历史用例的子 agent。找不到时在最终回复中说明。

# 背景（派发子 agent 时，把这一节原样附在任务里）
- 洛书是鸿蒙的 AI 伴随功能。swing_service 不实现算法，是系统级桥接与治理层，职责如下：
  1. 接入鉴权：SUBSCRIBE_SWING_ABILITY 权限、事件名→eventId 映射、domainId 校验
  2. 事件生命周期：订阅/退订、引用计数、睡眠/S4 不注册、相机互斥白名单、901/903 不支持预加载
  3. 参数下发：SwingParameter.json、SetParam 命令码 1/79/73、EnableEvent
  4. 数据通道：SendFileByFd、DataType→64/65/66/81/67/77、fd 关闭
  5. 设备状态注入：stateId=0 折叠相机切换、1 亮灭屏、2 旋转、3 折叠；903 专属 78 物理方向、80 折叠状态
  6. 结果分发：OnIgsEventDone→publishSwingEvent；901 结果不打日志
  7. 可靠性：OnServiceDied 重连、SensorHub 参数重放、HiSysEvent 打点
- 901 = ACTIVE_SCREEN_AWARENESS（屏幕感知），903 = GAME_OCR_UNDERSTAND（游戏理解）。
- 本次重点是多机型适配：三折叠、双折叠（内折）、阔折叠、小折叠（上下翻折）。重点关注用户在不同使用场景下洛书能否正常工作。
- AI伴随的用户交互（用例都按这套交互来写）：
  - 前提：设置中【AI伴随】开关开启（首次开机引导可选择是否开启；开启后默认开启，可在设置中关闭）。
  - 入口：双击导航条。桌面双击 → 无屏伴随；应用中双击 → 小屏伴随。
  - 无屏伴随：有动效，导航条变色。桌面上只能是无屏伴随。
  - 小屏伴随：让出部分显示区域，含【识别屏幕】、【点击/按住说话】、【叉号】（退出）按钮。识别屏幕后出现与屏幕内容相关的推荐问题气泡（如打开图库时出现“云图库备份一般如何节省本地空间？”），点击气泡即以气泡内容提问并进入大屏伴随。
  - 大屏伴随：约占半屏。说话按钮变大并多出键盘图标（可打字）；中间显示 AI 回复；识别屏幕后仍出现气泡；另有【禁止外放】和【伴随记录】按钮。
  - 状态切换：应用中可拖动伴随区域，在无屏/小屏/大屏之间切换。伴随中从桌面打开应用 → 自动变为小屏伴随；从应用回到桌面 → 自动变为无屏伴随。
  - 形态限制：部分折叠形态不能进入伴随，例如三折叠完全折叠成单屏时不能双击导航条进入；双折叠折叠态外屏可以进入。每个机型的每个形态都要测入口是否可用。
- 洛书不支持某些场景是正常的。不支持的场景要验证“正确拒绝”：不工作或给出提示、不闪退、日志无 error 级异常、退出该场景后无需重新开启即可恢复。
- 用例由测试人员拿真机手工执行，同时抓 hilog 核对。步骤里不能出现调用接口、root、kill 系统服务这类操作；这类测试点放入 NON_MANUAL。

# 子 agent 使用规则
1. 子 agent 看不到你的上下文。每个子 agent 的任务说明都必须自包含，至少写明：背景一节、它负责的范围、输入文件的路径、输出文件的路径和格式、完成标准。
2. 所有子 agent 的产出一律写入 docs/luoshu/review_work/ 目录下的文件（下文简写为 review_work/）。不要在源码目录的其它位置创建或修改文件。子 agent 回复你时只给一段简短摘要（做了什么、发现的主要问题），不要把全文贴回来。你通过读文件汇总结果。
3. 同一阶段内的子 agent 同时派发，不要一个做完再派下一个。并发数受限时，分批派发，每批尽量多派。
4. 子 agent 涉及源码的结论都必须带“文件名:行号”或函数名。找不到依据时写“无法从源码确认”，并注明需要问业务方、算法方还是 DMS。禁止编造。
5. 某个子 agent 失败或产出不合格时，重新派发一个新的子 agent 重做，并在任务说明里写清上次哪里不合格。

# 工作流程

## 阶段 1：并行收集信息（共派发 8 个子 agent，同时进行）

### 1A～1D：源码事实提取（4 个子 agent，按领域拆分）
| 子 agent | 负责领域 | 输出文件 |
|---|---|---|
| 1A | 接入鉴权、订阅/退订、引用计数、睡眠/S4 判断与恢复、相机互斥白名单、订阅方死亡清理 | review_work/facts_lifecycle.md |
| 1B | FoldStatus→注入值完整映射表（是否覆盖三折叠扩展状态 *_WITH_SECOND_*，未知状态怎么处理）、HALF_FOLD 的 DisplayMode 判断、外屏（MAIN/SUB）特殊处理、折叠相机切换 stateId=0 的触发条件与 cameraId | review_work/facts_fold.md |
| 1C | 旋转：phyrotation.offset、rotation_correction、PC 旋转偏置的读取与计算；平放（方向不确定）时的处理；pc/pad/tv judge 判断条件 | review_work/facts_rotation.md |
| 1D | 参数下发、SendFileByFd、结果分发、可靠性、打点；投屏/外接屏/分屏/多用户/省电模式下的特殊处理；AI伴随的哪个操作触发订阅/退订（双击进入、识别屏幕、退出、无屏/小屏/大屏切换），游戏场景识别走 903 还是 901 | review_work/facts_misc.md |

每个子 agent 还必须输出：
- 本领域各职责在源码中实际打印的日志关键字或打印格式（用于替换用例里的“建议关键字”）；
- 如果源码或配置中能找到各机型、各形态、各方向的期望注入值，一并列出；
- 对 cases.py 中 SCENARIOS 里属于本领域的场景，给出结论：支持 / 不支持 / 部分支持 / 无法确认。
- 行为基线：对 cases.py 中 BASELINE 里属于本领域的用户操作，按源码写出以下内容。缺少的用户操作可以新增行：
  - 应有行为：该操作触发的函数调用链和正常日志序列；
  - 不应出现的行为：出现即说明 swing_service 有问题；
  - 实际日志关键字；
  - 预期内的告警：正常流程中也会打印的 warn/error，例如不支持形态下拒绝时打印的告警。这些不算问题，避免测试人员误报；
  - 源码依据。
- 本领域可能出错的地方：异常分支、错误码、重试或兜底逻辑。这些对应的报错日志列为“不应出现”，供测试时检索。

### 1E～1H：用户使用场景挖掘（4 个子 agent，每个机型一个，与 1A～1D 同时进行）
- 每个子 agent 只负责一个机型：1E 三折叠、1F 双折叠、1G 阔折叠、1H 小折叠。
- 任务：站在真实用户的角度，穷举这台折叠机的日常使用方式。至少考虑：
  - 握持方式：单手、双手、横持、竖持；
  - 各形态：外屏、内屏、半折悬停、立放；
  - 形态切换：开合时机、应用接续、应用重启；
  - 场所：桌面平放、躺着、走路、乘车；
  - 和其它功能叠加：相机、视频通话、游戏、分屏、投屏、充电、保护壳；
  - 伴随各状态（无屏/小屏/大屏）与形态切换的组合：伴随进行中开合、切换到不能进入伴随的形态后再切回；
  - 洛书大概率不支持的场景。
- 对照 cases.py 中该机型和公共用例的现有内容，输出“未覆盖的使用场景清单”，每条说明场景、用户为什么会这样用、可能出的问题，写入 review_work/scenarios_<机型>.md。
- 这 4 个子 agent 不需要读源码。

## 阶段 2：合并源码事实（主 agent）
把 facts_*.md 合并为 review_work/源码事实.md，完成 SCENARIOS 的确认，并把行为基线填入 cases.py 的 BASELINE。每一行的七个字段都要填写，确实无法确认的写“无法从源码确认”。如果 4 份文件之间有矛盾，派一个子 agent 只针对矛盾点回到源码复核，再根据复核结果裁决。

## 阶段 3：分页评审（5 个子 agent 并行）
每个子 agent 负责一页：公共、三折叠、双折叠、阔折叠、小折叠。输入：源码事实.md、历史用例、该页现有用例，机型页再加上对应的 scenarios_<机型>.md。要求：
1. 逐条评审，结论为：保留 / 修改 / 删除 / 合并到某条 / 转非手工。
2. 场景支持性以源码事实.md 为准，填：支持 / 不支持 / 部分支持 / 无法确认。不支持的用例，预期结果改为“正确拒绝”的写法。
3. 日志核对点里的“建议关键字”，替换为源码事实.md 中的实际关键字。每条用例的“swing_service 核对点”必须和 BASELINE 中对应用户操作的“应有行为 / 不应出现的行为”一致。用例里有、但 BASELINE 没有覆盖的用户操作，补到 BASELINE。
4. 把 scenarios_<机型>.md 里有价值的场景写成新用例。每个机型至少覆盖以下维度：各形态入口是否可用（桌面和应用中分别双击导航条）、初始状态注入、折叠状态映射、半折判断、各屏幕四个方向、相机切换、切屏不误报灭屏、伴随各状态下开合不中断（或在不支持的形态中正确退出）、快速开合。
5. 写法参考历史用例的粒度和措辞。
6. 输出两个文件：
   - review_work/cases_<页名>.py：该页修改后的完整用例列表，符合下方“格式约束”；
   - review_work/review_<页名>.md：评审记录，每条一行：编号 | 结论 | 支持性 | 源码依据 | 修改说明。

## 阶段 4：交叉核查（5 个子 agent 并行，和阶段 3 不能是同一个子 agent）
每个核查子 agent 负责一页，只做核查，不做创作：
1. 核对该页所有“源码依据”，以及 BASELINE 中与该页相关的行：打开源码确认对应行确实存在、内容和结论一致。
2. 在源码中搜索该页每个日志关键字，确认确实会打印。
3. 检查支持性结论是否和源码事实.md 一致；不支持的用例，预期结果是不是“正确拒绝”的写法。
4. 检查步骤能否在真机上手工完成，测试步骤和预期结果的条数是否一一对应。
5. 输出 review_work/verify_<页名>.md，列出发现的问题和修正建议。
主 agent 根据核查结果修正 cases_<页名>.py；改动较大的页，重新派一个子 agent 修改。

## 阶段 5：合并、生成与终检
1. 主 agent 把 5 份 cases_<页名>.py 合并进 cases.py：
   - 去掉重复：公共用例已覆盖的，不再在机型页重复；四个机型页都出现的同类用例，上移到公共用例。
   - 原有编号保持不变；新增用例按页往后编号；删除的用例直接删掉。
   - 更新 SUPPORT（每条用例的支持性，默认“支持”）、SCENARIOS（初判列改为确认结论，并附源码依据）、NON_MANUAL。
   - 如果新增用例用了新的覆盖维度标签，同时加到 cases.py 的 DIMS 列表中。
2. 在源码根目录运行：python3 docs/luoshu/gen.py docs/luoshu，生成 Excel 和 md。如果源码事实.md 中有期望注入值，用 openpyxl 填入 Excel《预期值对照表》的黄色单元格。然后把生成的 Excel 另存为 docs/luoshu/洛书多机型适配测试用例_终版.xlsx。
3. 派 1 个全新的质检子 agent（没有参与过前面任何阶段），对照下面的“终检清单”独立检查最终 Excel，输出 review_work/final_qa.md。主 agent 修完质检发现的问题后，重新生成 Excel。

终检清单：
- 每条用例的测试步骤和预期结果条数一一对应，编号连续
- 没有残留“待确认”；“无法确认”必须写明原因和该问谁
- 源码依据和日志关键字都经过阶段 4 核查
- 所有步骤都能在真机上手工完成，预期结果可以观察、可以判定
- 四个机型都覆盖了阶段 3 第 4 条列出的全部维度（查看 Excel《覆盖矩阵》页）
- 预期不支持的用例，预期结果都是“正确拒绝”的写法
- 每条用例同时有功能表现（目标 1）和 swing_service 核对点（目标 2）
- BASELINE 每一行的七个字段都已填写，并且经过阶段 4 核查
- 公共用例和机型用例之间没有重复
- gen.py 运行成功，Excel 能正常打开

# 格式约束（cases.py 的数据结构，不能改）
每条用例是一个 8 元组：
("编号", "级别 L0/L1/L2", "用例名称", [预置条件...], [测试步骤...], [预期结果...], [日志核对点...], [覆盖维度标签...])
- 测试步骤和预期结果的列表长度必须相等，第 i 条预期对应第 i 条步骤
- 用例名称参考格式：“首次开启光环境健康检测，按照引导操作”，即说明用户在做什么
- 交互术语统一用：【AI伴随】开关、双击导航条、无屏伴随、小屏伴随、大屏伴随、【识别屏幕】、气泡、【叉号】、【禁止外放】、【伴随记录】
- 编号前缀：LS_COMM_ / LS_TRI_ / LS_DUAL_ / LS_WIDE_ / LS_FLIP_

# 最终交付
1. docs/luoshu/洛书多机型适配测试用例_终版.xlsx（主交付物）。包含以下页：说明、公共用例、三折叠、双折叠、阔折叠、小折叠、日志核对指南、预期值对照表、覆盖矩阵、支持场景清单、非手工覆盖项
2. review_work/源码事实.md
3. docs/luoshu/评审记录.md：汇总 5 份 review_<页名>.md，并统计各页新增、修改、删除的条数，以及阶段 4、阶段 5 发现并修正的问题数
4. 更新后的 docs/luoshu/cases.py
如果运行环境无法执行 Python：按 洛书多机型适配测试用例.md 的现有格式，输出 docs/luoshu/洛书多机型适配测试用例_终版.md 作为主交付物，并在回复中说明原因。

完成后，用不超过 15 行回复：各阶段派发了多少个子 agent、最终用例条数（公共 + 各机型）、哪些场景“无法确认”需要找谁、交付文件的路径。
```
